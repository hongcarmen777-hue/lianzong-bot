# 小苹果 v0.2.7

在 v0.2.6 已经打通的 CloudBase MySQL 持久化链路上，新增“报名一表”后台。

核心原则：

- 完整恋综：骰主私聊 `录入恋综 P1` → 发资料 → `录入完成`。
- 报名一表：骰主私聊 `录入一表 P1` → 发一表 → `录入完成`。
- 两种资料都保存**完整原文**，同时建立结构化索引。
- 一表单独存放在 `xp_applications`，不和恋综档案 `xp_shows` 混在一起。
- 一表原文默认只在骰主私聊后台使用，不主动在主群泄露。
- 主群继续负责基于 `xp_shows` 的选本、身份牌查询和推荐。

## 从 v0.2.6 升级：先建 1 张新表

如果现有 v0.2.6 已经正常运行，只需要在 CloudBase：

`SQL 型数据库 → SQL 编辑器`

执行仓库根目录的：

`add_xp_applications.sql`

成功后“数据库表”里会比原来多一张：

`xp_applications`

然后再部署 v0.2.7。

v0.2.7 启动时会检查这张表是否存在；没建表就不会假装功能正常。

## 一表怎么录

骰主私聊：

```text
录入一表 P1
```

然后直接把收到的一表正文粘给小苹果。可以一条发完，也可以拆成多条。最后发：

```text
录入完成
```

成功后会回复类似：

```text
一表落库成功。#12｜P1｜阿北｜意向 03｜v1
```

其中 `#12` 是这张一表在数据库里的 ID。

## 一表怎么查

骰主私聊可以用：

```text
一表列表
一表列表 P1
查看一表 12
```

也可以直接自然语言问，例如：

```text
P1 现在都收了哪些一表？
阿北想玩什么？她有什么雷点？
结合 P1 身份牌，你觉得阿北更适合哪张？为什么？
```

小苹果会把已录入的一表结构化索引提供给 DeepSeek，同时仍然以数据库原文为底稿。

## 同名一表更新

如果同一届、同一个识别名称再次录入，例如 `P1 + 阿北`，会更新原记录并把 `version` +1，而不是无限制造重复行。

如果一表里完全没有可识别名称，会作为新的一张一表保存。

## 一表保存什么

`xp_applications` 会保存：

- 所属恋综编号 `show_code`
- 报名者/角色可识别名称 `applicant_name`
- 性别、年龄（仅原文明确写出时）
- 意向身份牌
- 检索 TAG
- 偏好、雷点/边界
- 原表字段的结构化 JSON
- AI 概括
- **完整原文 `raw_text`**
- 原始分段 `raw_chunks_json`
- 版本号

AI 解析失败时也不会丢原文；本地解析器会尽量保留常见的“字段：内容”。

## 数据库状态

发送：

```text
数据库状态
```

v0.2.7 会显示恋综数、一表数和当前草稿数，例如：

```text
小苹果 v0.2.7｜数据库：CloudBase MySQL HTTP API（持久化）｜恋综 2｜一表 7｜草稿 0
```

## 环境变量

沿用 v0.2.6 已经配置成功的变量即可，不需要新增 Key：

- `TCB_ENV_ID`
- `TCB_API_KEY`（或现有兼容的 CloudBase API Key 注入变量）
- `QQ_APP_ID`
- `QQ_APP_SECRET`
- `DEEPSEEK_API_KEY`
- `DEEPSEEK_MODEL`（保持你当前线上已经能正常调用的值即可）
- `CLAIM_TOKEN`
- `PORT=8080`

不用配置 MySQL 公网地址，也不用 VPC 直连。
